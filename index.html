Darmowe odpowiedniki

Zamiast aktualizować płatny produkt, plan może przewidzieć przejście na bezpłatny odpowiednik (np. Oracle Database → PostgreSQL, Oracle JDK → Amazon Corretto, RHEL → AlmaLinux). Uwzględniane są godziny migracji, ryzyka zgodności i brak opłat licencyjnych.

Suwak ustawia miesiąc przejścia na nową wersję (go‑live) — w starym scenariuszu przesuwa kroki planu danego składnika, w nowym wdrożeniu ustala datę najbliższej migracji. Pole godzin zastępuje szacowaną pracochłonność migracji (puste = wartość automatyczna).

    Podsumowanie według składnika

    Zaawansowane: parametry składników i zależności

    Edytuj daty, częstotliwość aktualizacji, liczbę CVE, opóźnienie poprawek, godziny prac i zależności. Zmiana wersji tutaj aktualizuje też szybki wybór. Daty to przybliżenia z publicznych cykli życia (stan na koniec 2026); wersje i daty z gwiazdką (*) to prognozy.

    Jak liczy symulacja

    • Nowe wdrożenie: każdy składnik w wybranej serii (domyślnie najnowszej wspieranej) z kompletem poprawek; dalej regularne aktualizacje, obsługa CVE i — jeśli włączone — migracje przed końcem dostępnych poprawek.
    • Stary serwer — bez aktualizacji: stare wersje, nikt nie instaluje poprawek. Zaległe podatności od daty ostatnich poprawek plus nowe CVE kumulują się; dla krytycznych i wysokich liczone są tylko mitygacje (zabezpieczenia zastępcze).
    • Stary serwer — z planem: etap 0 (inwentaryzacja, analiza zgodności, triage zaległych CVE), etap 1 (doinstalowanie zaległych poprawek w seriach jeszcze wspieranych), następnie migracje według planu. W miejscu — kolejno, z krokami pośrednimi tam, gdzie producent wymaga (np. RHEL 7→8→9, MySQL 5.7→8.0→8.4, Oracle przez 19c). Nowy serwer — budowa nowego środowiska z wersjami docelowymi i jedno przełączenie.
    • CVE: proces Poissona o intensywności CVE/rok × mnożnik trendu (stały 1; wykładniczy (1+g)t; liniowy 1+g·t). Ważność: 12% krytyczne, 35% wysokie, 43% średnie, 10% niskie. Każda wymaga weryfikacji. Krytyczne/wysokie: mitygacja, jeśli poprawka nie zdąży w SLA; aktualizacja awaryjna, jeśli najbliższa planowa nie mieści się w SLA. Po EOL — tylko mitygacja, podatność pozostaje otwarta do migracji.
    • Testy: × (1 + współczynnik regresji × liczba składników zależnych, także pośrednio). Migracja = godziny migracji + pełna regresja.
    • Płatne wsparcie: okresy oznaczone jako płatne (np. Windows 10 ESU, Windows Server/SQL Server ESU, RHEL ELS, Ubuntu Pro ESM, Oracle Extended Support, Oracle Java SE) dają poprawki tylko po wykupieniu. Przy opcji „Niewykupione” poprawki kończą się wraz z darmowym wsparciem. Aktualizacje RHEL wymagają aktywnej subskrypcji.
    • Zakupy: Windows Server i SQL Server — nowa wersja to nowa licencja (chyba że jest Software Assurance); Windows 10/11 Pro — nowe wersje bezpłatnie, LTSC i zmiana kanału — nowa licencja; Oracle XE/Free — bezpłatna, bez wsparcia; Oracle Database — nowa wersja w ramach aktywnego wsparcia; RHEL — w ramach subskrypcji; pozostałe składniki są bezpłatne.
    • Produkt niebezpieczny: krytyczna lub wysoka podatność otwarta dłużej niż SLA w składniku, którego nie da się załatać (EOL, niewykupione wsparcie, brak aktualizacji). Mitygacje ograniczają ryzyko, ale go nie usuwają.
    • Mitygacje: gdy poprawki nie ma albo nie zdąży w SLA, liczona jest mitygacja (zabezpieczenie zastępcze). Z prawdopodobieństwem równym „skuteczności” chroni ona od momentu wdrożenia — taka podatność nie czyni produktu niebezpiecznym, ale pozostaje otwarta do załatania. Nieskuteczna lub niemożliwa mitygacja nie zmienia oceny zagrożenia.
    • Darmowe odpowiedniki: w starym scenariuszu zamiana zastępuje aktualizację w planie modernizacji; w nowym wdrożeniu odpowiednik jest wdrażany od początku (ok. 3 miesiące adaptacji aplikacji). Po zamianie składnik ma terminy wsparcia, tempo podatności i godziny prac odpowiednika.
    • Ręczne daty migracji: suwak w planie ustawia miesiąc go‑live migracji składnika, a pole godzin — jej pracochłonność. IIS jest częścią Windows: jego wersja i wsparcie wynikają z systemu, a migracja następuje razem z migracją systemu.
    • Dane: tempo podatności w symulacji pochodzi z data/vulnerabilities.json (pole „rate”); składniki z większą liczbą wpisów w katalogu CISA KEV są częściej celem fal 0‑day.
    • Zgodność: reguły dla typowych pułapek (javax→jakarta, wymagana wersja Javy, VC++ dla Apache/PHP na Windows, certyfikacja Oracle/SQL Server na danym OS, OpenSSL 3, wersje PHP/Python w repozytoriach, glibc dla Node.js itp.). To lista kontrolna, nie gwarancja — sprawdź dokumentację producentów.

    Informacje prawne

    • Charakter strony. Strona ma charakter poglądowy i edukacyjny. Produkt, którego dotyczy symulacja, jest fikcyjny, a wyniki zależą od przyjętych założeń i losowania — nie gwarantują bezpieczeństwa, kosztów ani harmonogramu.
    • Podatności w symulacji są zmyślone. Wszystkie podatności pokazane w symulacji (identyfikatory w formacie SIM‑RRRR‑NNNN, daty, ważność, fale 0‑day) są generowane losowo. Nie są to wpisy CVE ani informacje o rzeczywistych lukach w wymienionych produktach.
    • Aktualne podatności są prawdziwe. Sekcja „Aktualne podatności (CISA KEV)” pokazuje publiczne wpisy z katalogu Known Exploited Vulnerabilities agencji CISA, przypisane do produktów automatycznie po nazwie producenta i produktu — przypisanie może być nieprecyzyjne (np. wpisy jądra Linux przy każdej dystrybucji). Dane są aktualne na dzień podany przy sekcji.
